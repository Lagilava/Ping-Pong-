# Mobile app and Play Store launch

**Short answer: yes.** The game already runs on Android Chrome with full
WebGL, touch controls, fullscreen and landscape lock, so a Play Store app does
not need a rewrite. The recommended path is to ship the existing web game as a
**Trusted Web Activity (TWA)**: an Android app that opens the GitHub Pages
site in Chrome with no browser bar. Every push to `main` updates the app
instantly, with no new store release.

## Paths compared

| | **PWA + TWA (Bubblewrap)** (recommended) | Capacitor wrapper | Native rewrite (Unity, Godot, Kotlin) |
|---|---|---|---|
| Code changes | None beyond what is in the repo now | Build step, copy `game/` into an Android project | Rewrite every mode, the renderer, online play |
| Rendering | Real Chrome: same WebGL, same speed as the site | Android System WebView (Chromium, usually close) | Native, but all art and shaders redone |
| Updates | Push to `main`, live in ~2 min | New store release for every change | New store release for every change |
| Offline | Service worker (added, see below) | Everything bundled in the APK | Bundled |
| Online play (PeerJS/WebRTC) | Works as on the site | Works in WebView | Rewrite netcode |
| Play Games, in-app billing, haptics | Billing via Digital Goods API; no Play Games | Native plugins for all of it | Everything |
| Download size | ~1 MB app, assets fetched/cached | ~70 MB (music) unless trimmed | Varies |
| Time to first store build | A day of the owner's time | A few days | Months |

**Recommendation:** launch with a TWA. Move to Capacitor only if you later
want Play Games achievements and leaderboards, native ads, or a build that
works with zero network on first launch. A native rewrite would throw away the
art, shaders and netcode for no gain a player would notice.

iPhone: the App Store rejects thin web wrappers, so iOS stays a Home Screen
web app (already supported, with the one-time "Add to Home Screen" tip). A
Capacitor build is the route if the App Store ever matters.

## What is now in the repo

- `game/manifest.webmanifest`: installable, fullscreen, landscape, with proper
  maskable icons (`assets/icons/icon-maskable-*.png`; the artwork sits inside
  the Android adaptive-icon safe zone).
- `game/sw.js` + `game/js/app/pwa.js`: a service worker so the app starts and
  plays offline. Code and pages are **network first**, so online players always
  get the latest push; art and fonts are served from cache and refreshed in the
  background. Music and range requests are never intercepted (they stream as
  before). When the game runs installed (Home Screen or TWA), it caches all
  24 MB of code and art once, in the background after load, so every mode works
  offline. Add `?nosw` to a URL to skip registration while debugging.
- `game/offline-assets.json`, generated by `node tools/build-offline-assets.js`.
  **Rerun it after adding, renaming or deleting files under `game/`**
  (`--check` tells you if it is stale; editing files does not need a rerun).
- `android/twa-manifest.json`: Bubblewrap config (package
  `io.github.lagilava.pingpong`, landscape, fullscreen, start URL
  `/Ping-Pong-/game/`). `android/assetlinks.template.json` is the Digital Asset
  Links file to publish. `android/.gitignore` keeps the keystore and build
  output out of git.
- `docs/play-store/`: privacy policy draft, store listing text, and the listing
  graphics (icon, feature graphic, screenshots).

## Asset size plan

The game is ~67 MB, of which **42 MB is five music tracks at 320 kbps MP3**.
Art and code are 24 MB.

1. Music already streams (it is not downloaded before play) and the service
   worker leaves it alone, so it does not block start-up.
2. Optional, owner's call because it touches audio quality: re-encode the
   tracks to 192 kbps AAC/Opus (about 60% smaller, generally transparent) and
   serve `.m4a`/`.opus` with an MP3 fallback. Not done, since the project rule
   is no fidelity trade-offs without sign-off.
3. Optional offline music for the installed app: cache each mode's track the
   first time it plays and serve byte ranges from the cache in `sw.js`. Not
   done yet; the app plays offline without music today.
4. A Capacitor build would bundle everything; keep the AAB under Play's 200 MB
   base limit (it would be ~70 MB as is).

## Play Store launch checklist

Items marked **Owner** need your accounts, money, identity or legal judgment.

1. **Owner: music rights. This is the biggest blocker.** The built-in tracks
   include *Axel F* (a commercial, copyrighted song) and four others whose
   source is not recorded in the repo. A store listing with music you do not
   have a licence for gets removed and can get the developer account banned.
   Replace them with tracks you own or that are licensed for commercial use
   in apps (for example royalty-free libraries, or commission your own), and
   record the source and licence of each in the repo.
2. **Owner: Google Play developer account.** One-time US$25 fee, identity
   verification (legal name, address, phone; a D-U-N-S number if you register
   as an organisation).
3. **Owner: personal accounts must run a closed test first**: at least 12
   testers opted in for 14 continuous days before you can apply for
   production. Recruit friends early.
4. **Owner: Digital Asset Links** (removes the browser bar). The file must be
   served at `https://lagilava.github.io/.well-known/assetlinks.json`, the
   domain root, which this repo cannot serve because it is a project site under
   `/Ping-Pong-/`. Either create the repo `Lagilava/Lagilava.github.io` and add
   `.well-known/assetlinks.json` there (plus an empty `.nojekyll`, or Jekyll
   hides the `.well-known` folder), or point a custom domain at this repo. Fill
   in both SHA-256 fingerprints: the upload key (from `bubblewrap fingerprint`)
   and the Play App Signing key (Play Console > Test and release > App integrity).
5. **Owner: build and sign.** On your PC: install Node 18+, then
   `npm i -g @bubblewrap/cli`, `cd android`, `bubblewrap build` (it offers to
   download the JDK and Android SDK and to create `android.keystore`).
   Back up the keystore and its passwords somewhere safe and never commit them;
   enrol in Play App Signing so a lost upload key can be reset. Upload
   `app-release-bundle.aab`.
6. **Target API level.** New apps and updates must target Android 16
   (API 36) since 31 August 2026. Use a current Bubblewrap release, which sets
   this, and check the Console's warning before each upload; the bar rises every
   August.
7. **Owner: privacy policy URL.** Required because online play connects to third
   parties. Review `docs/play-store/privacy-policy-draft.md`, put your contact
   email in it, then publish it (for example as `privacy.html` on Pages).
8. **Owner: Data safety form.** Draft answers are in the privacy policy draft:
   no account, no analytics, no ads; settings and progress stay on the device;
   online play shares the IP address with the other player and with the
   matchmaking/relay servers (PeerJS, public MQTT brokers, Metered TURN) to set
   up the connection; nothing is sold.
9. **Owner: content rating (IARC questionnaire).** Expected result: Everyone /
   PEGI 3. Answer "yes" to users interacting online (players connect peer to
   peer, no chat). Mention the cartoon zombies and the AI's trash talk lines.
10. **Owner: target audience.** Choose 13+ unless you want to meet the
    Families policy (stricter ad and data rules).
11. **Store listing.** Text and graphics are drafted in `docs/play-store/`:
    512x512 icon, 1024x500 feature graphic, 1920x1080 landscape screenshots.
    Category Games > Sports. Review the wording, then paste it in.
12. **Before release, test on real phones** (this has only been tested in
    desktop Chromium with phone emulation): install the closed-test build,
    check that the browser bar is gone (asset links working), every mode
    starts, touch controls, sound after the first tap, offline launch in
    airplane mode, and an online match between two phones on mobile data.
13. **Optional later:** Play Games Services, in-app purchases (Digital Goods
    API), a Capacitor build for full offline and native features.

## Day-to-day after launch

Pushes to `main` reach app users as soon as Pages redeploys. Rebuild and upload
a new AAB only when `android/twa-manifest.json` changes (icon, name, colours,
version) or Play raises the target API level. Bump `appVersionCode` each time.
